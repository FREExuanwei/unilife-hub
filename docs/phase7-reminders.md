# Phase 7 — local timer reminders

Timer completion always saves the timer transition, learning record (focus only), and page notice before attempting optional browser cues. `ReminderFeedback` is mounted in the shared layout inside `CourseProvider`, so its completion card appears on every route. The notice remains in the course snapshot through refresh until the user closes it or starts another timer. Manual early save and reset do not emit reminders.

## Settings and browser behavior

`unilife-reminder-settings:v1` stores the strict version-1 preference object: `sound`, `vibration`, and `notifications` booleans. Sound and vibration default on; notifications default off. Parsing projects only these supported fields, so a portable backup cannot carry claim history, permission prompts, or arbitrary extra reminder data.

`ReminderSettingsPanel` provides accessible switches, a user-triggered sound preview, capability notices, and explicit storage errors. Preferences update under the existing `unilife-hub:write` lock, re-reading the latest settings inside that lock. A pending recovery journal blocks preference writes. The low-level synchronous `writeReminderSettings` is for an already-locked transaction; application UI uses `saveReminderSettings`. Restore dispatches `unilife:data-restored`, which reloads reminder settings. Other tabs receive the normal `storage` event.

Web Audio uses a quiet sine-wave envelope lasting under one second: three ascending notes for focus, two descending notes for a break. A start, resume, sound-enable, or preview click creates/resumes the AudioContext. Completion never tries to unlock audio automatically. A freshly reloaded page may therefore be unable to play a restored expired timer's sound until another user gesture; the saved completion card still appears.

Vibration is attempted only if `navigator.vibrate` is available and the preference is enabled. Browser support, device hardware, user activation rules, OS settings, and background suspension can prevent physical feedback; these conditions do not affect timer persistence.

The system notification switch is the only permission-request entry point. Granted permission enables notifications; denied, dismissed/default, insecure, and unsupported states use the page card. A small durable prompt marker (`unilife-reminder-permission:v1`) prevents another request after a default/dismissed result, including refresh. Users can change permission in their browser's site settings; the app does not repeatedly prompt. Notification creation checks current permission and catches browsers that do not support constructor-based notifications. The app uses no service worker push or background timer delivery. Browser notifications use a per-cycle tag and are silent, leaving sound to the user's separate sound setting.

## Completion ownership

The successful completing writer runs under the shared Web Lock and appends the cycle ID to `unilife-reminder-claims:v1` before optional feedback. Every tab and StrictMode replay observes the same completed timer/claim. Vibration and notification belong to this completing writer. Audio uses a separate `unilife-reminder-sound-claims:v1` ledger: an untouched tab without an unlocked AudioContext cannot consume sound delivery. An audio-ready tab observing the saved completion may claim and play that sound exactly once under the same lock. Storage observers do not replay vibration or notification. Both ledgers retain the latest 256 claims and are excluded from portable backups; the persisted completed timer protects older cycles. Portable backups omit active timer state, so restoring one cannot revive an old completed cycle. A browser-reopened expired active timer follows the normal timestamp check. Pause or finish at or after the exact expiry also follows natural completion; feedback detection uses the resulting state rather than just the requested action name.

If a timer save fails, no cue is emitted. If saving the claim or reading reminder preferences fails, completion remains saved, optional cues are suppressed, and an explicit error explains that page feedback is available. This gives at-most-once physical delivery for a persisted cycle. As with any browser-side external effect, a process crash between a durable claim and the cue can suppress that cue; it cannot replay it after refresh. The persisted page notice provides the durable fallback. A closed or suspended browser cannot guarantee exact real-time delivery.

## Verification

`node --test tests/reminders.test.mjs` contains 16 native Node tests with injected browser/storage boundaries. Initial red tests failed because the feature was absent, then passed after implementation. Recovery-lock and final-review regression cases also failed before their fixes. Coverage includes strict settings, blocked/quota storage, durable claims, persistence-before-cue ordering, no manual reminders, restored expired breaks, natural completion on an expired pause/finish, an untouched completing tab handing audio to the initialized tab, permission states, no repeated prompt, user-unlocked audio, preference gates and unsupported browser fallback.

The integrated production browser harness passed 11 groups, including real two-tab ownership, refresh/restart and exact-boundary completion. Browser AudioContext, vibration and Notification effects were instrumented to verify calls and duplicate prevention; actual speaker output, vibration hardware and operating-system banners still need device acceptance. The detailed final report is `phase7-verification.md`.

For a real browser harness on localhost or HTTPS:

1. Load the app with `React.StrictMode`, open Settings, and confirm the default switches and an empty page notice. Click “试听提示音”; only sound should play, and no permission dialog should appear.
2. Change focus and break durations to one minute. Start a focus timer, navigate to another route, and wait for completion. Confirm a global card and exactly one learning record, one short sound/vibration attempt, and no notification while its preference is off. Refresh: the card remains, and optional cues do not replay.
3. Open a second tab on the same origin before completion. Capture browser audio/vibration/Notification constructor calls in both pages. Their combined count must be one logical cue per completed cycle; the claim is visible in localStorage and both tabs display the saved notice. Pause/resume must preserve the cycle ID and still complete once.
4. Start a break and allow it to expire. Confirm the different short sound and global card without a learning record. Save an early focus, discard/reset another, and verify neither produces a completion cue or system notification.
5. Click the notification switch with a permission harness returning `granted`, `denied`, and `default`. Granted should persist `notifications:true`; the other states should persist false and explain the fallback. After default, repeat the click and refresh; the request count must remain one. Never trigger a permission request by mounting, navigating, starting a timer, or completing it.
6. Stub AudioContext unavailable/rejecting, vibrate unavailable/throwing, and Notification unavailable/throwing. The saved timer transition and global card must still succeed without an uncaught error.
7. Inject `getItem`/`setItem` errors. Broken reminder preferences disable edits without overwriting raw data. A failed completion snapshot write must produce no cue or claim. A failed claim write must leave completion and its page card saved, report the storage error, and suppress optional cues.
8. Restore a valid backup while Settings is mounted. Verify switches refresh after `unilife:data-restored`. Insert a prepared recovery journal and attempt a preference update under the hub lock; raw reminder settings must stay unchanged until recovery finishes.
9. Review Settings and the global card at 1440px and 390px widths in light/dark themes, with keyboard focus and forced colors. The card must stay above mobile navigation, allow dismissal, and avoid covering its own close control.
